# Precision trade-offs, measured

Generated by `Scripts/quantization-report.py`. Apple M1 Pro, 16 GB, 30 s of
audio, three timed runs per case with process isolation and a cooldown.

The user-facing version of this is `MODEL-PRECISIONS.md`, rendered by the same
script with `--public`. This one keeps the size ratio, the LSD column, the
benchmark run identifiers and the short verdict tags; that one spells the
verdicts out and drops anything a reader without this machine cannot use.

Verdicts live in `VERDICTS` in the script, not in this file, so the tables and the
recommendation cannot drift apart. Sizes fall back to `KNOWN_SIZES` when a
checkpoint has been deleted - several were, once measured.

Quality is each precision against **its own model's fp32 output**, not against
clean audio: it is what the precision costs, not what the model scores.

## Chatterbox TTS

Rates here divide by generated audio, not consumed audio (`RateBasis.output`), so
they are not comparable to the rows above. fp32, fp16 and 8bit all produced 3.80 s
for the same sentence, which makes those three directly comparable; 6bit and 4bit
sampled different token counts.

| fp16 | 1293 MiB | 3.80 s | 5.658 s | 0.67x | 3058 MiB |
| 8bit |  917 MiB | 3.80 s | 3.846 s | 0.99x | 2287 MiB |
| 6bit |  769 MiB | 3.95 s | 4.606 s | 0.86x | 2250 MiB |
| 4bit |  620 MiB | 3.18 s | 3.025 s | 1.05x | 2205 MiB |

No quality column, and not for want of trying: quantization reaches only `t3`
(219 modules) and `s3gen.flow` (423), both downstream of conditioning and sampled,
so two precisions do not produce comparable waveforms. `ve` and
`s3gen.speaker_encoder` hold zero quantized modules, which is why the conditioning
parity cases reproduce fp32 bit-for-bit at every integer width.

## MossFormerGAN SE, CoreML

Precision is fixed at conversion time, so these are two compiled `.mlpackage`
files rather than one model with a flag.

| precision | package | RTF | peak footprint | peak RSS | stddev | vs fp32 MLX reference |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| FP32 | 13 MB | 3.7x | 1656 MiB | 279 MiB | 0.681 s | 129.0 / 129.6 dB |
| FP16 | 7.6 MB | 4.2x | 302 MiB | 277 MiB | 0.010 s | 61.4 / 61.8 dB |

The one unambiguous precision win in this package. Resident memory is identical,
so the 5.5x is compressed pages - the fp32 path allocates ~1.4 GiB of transients
that get compressed, which also explains its 68x worse timing variance.

## What to ship

| model | choose | why |
| --- | --- | --- |
| MossFormerGAN SE (CoreML) | **FP16** | faster, 5.5x lower footprint, far more consistent |
| MossFormer2 SE | **fp16** | 58% faster than fp32, lowest memory, 70.1 dB |
| MossFormer2 SR | **fp32** | quantization changes nothing measurable; fp16 returns NaN |
| USS | **fp32** | fp16 is slower, uses more memory, and costs 57 dB |
| Chatterbox | **fp32 or 8bit** | 8bit matches fp32 speed at 1.7 GiB less peak; fp16 is 37% slower |

There is no rule here that generalises across models, and the backend matters more
than the bit width: CoreML fp16 is a real compute win, MLX integer quantization
mostly buys disk. Both directions flip per model - fp16 is the fastest option for
SE and the slowest for Chatterbox.
